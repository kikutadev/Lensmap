# Lensmap Map品質改善計画

Date: 2026-08-15
Status: Completed

## 1. 目的

Lensmap の `Map` を「図をたくさん出す機能」へ寄せず、**Exploreで得た理解を、その意味に合った構造で保存し、必要なときだけ最適なReact表現へ落とす成果物**へ改善する。

今回の中心原則は次の3点である。

1. **構造化できる理解は、生成時点で構造化する。**
2. **Mapの意味（definition / comparison / causal 等）と表示形式（text / table / flow / chart 等）を分離する。**
3. **Visualを強制しない。tableや文章中心の表示が最適なら、それを正式なMapとして扱う。**

例:

```text
「BlueGateとは何？」
  semanticKind = definition
  presentation = definition card / concise text

「RedisとMemcachedの違いは？」
  semanticKind = comparison
  presentation = table

「なぜAからCが起きる？」
  semanticKind = causal
  presentation = flow

「20時点の性能推移は？」
  semanticKind = quantitative
  presentation = chart
```

したがって、`table Map` や `chart Map` という分類にはしない。
Table / Chart / Flow は**表現方法**であり、Mapの意味そのものではない。

---

## 2. Mapの意味構造を第一級データにする

### 2.1 `MapSemanticKind`

`MapArtifact` に、表示形式とは独立した意味分類を追加する。

初期値は次の8種類とする。

```ts
type MapSemanticKind =
  | "definition"
  | "comparison"
  | "causal"
  | "process"
  | "hierarchy"
  | "timeline"
  | "quantitative"
  | "synthesis";
```

意味:

| kind | 何を理解したMapか | 典型的な表示 |
|---|---|---|
| `definition` | 用語・概念の意味 | definition card / narrative |
| `comparison` | AとB等の相違・共通点 | table / comparison |
| `causal` | 原因と結果 | flow |
| `process` | 処理順・データフロー | flow / ordered steps |
| `hierarchy` | 親子・包含・分類 | hierarchy / outline |
| `timeline` | 時系列・変遷 | timeline |
| `quantitative` | 数値比較・推移 | table / chart |
| `synthesis` | 単一型に収まらない要約・統合 | structured narrative +必要なblock |

この分類はユーザーに必ずラベル表示するためのものではない。
主目的は、生成・保存・preview・再生成を意味レベルで安定させることである。

### 2.2 「定義」を正式なMap構造にする

従来案の「定義ならnarrative-onlyでもよい」から一歩進める。

定義が取れる場合は、例えば次の構造として保存する。

```json
{
  "semanticKind": "definition",
  "title": "BlueGate",
  "primary": {
    "type": "definition",
    "term": "BlueGate",
    "definition": "...",
    "keyPoints": ["...", "..."],
    "sourceRefs": ["S1", "S3"]
  }
}
```

UI上は短い文章に見えても、内部では `term / definition / keyPoints / sourceRefs` が分離されている。

そのため、後から以下が可能になる。

- 一覧previewで定義だけ抜き出す
- Evidenceを対応させる
- definition cardとして安定表示する
- 将来別表示へ変えても意味情報を失わない

**「文章しか表示していない」ことと「内部も非構造化テキストである」ことは別物として扱う。**

## 3. Map構造とReact表現の関係

### 3.1 現在の `lensmap-viz`

現在 `packages/visualization/src/schema.ts` には、安全なJSON DSLが既に存在する。

```text
comparison
flow
hierarchy
timeline
matrix
callout
chart
```

Chrome Extension側の `VisualizationBlock.tsx` がZod検証後、このJSONをReact componentへ変換している。

つまり、現状でも以下の流れは成立している。

```text
Codex
  ↓ lensmap-viz JSON
Zod allow-list
  ↓
React renderer
  ↓
Comparison / Flow / Chart ...
```

これは継続利用する。

### 3.2 Mermaidとstructured JSONの役割を分ける

今後の優先順位は次とする。

```text
1. Lensmap structured JSON
2. Markdown table / narrative（単純な内容）
3. Mermaid（DSLで自然に表現できない図だけ）
```

Mermaidを廃止する必要はないが、Mapの主要な構造保存形式にはしない。

理由:

- structured JSONならZodで意味を検証できる
- React previewを安定生成できる
- sourceRefsを構造的に保持できる
- 将来semantic edit / regenerateしやすい
- raw Mermaid文字列よりMapの意味を再利用しやすい

Mermaidは複雑な関係図などに使えるescape hatchとして維持する。

### 3.3 structured rendererを少し拡張する

現在のvisualization schemaへ、Mapで頻出するtext-centricな構造を追加する。

最低限:

```text
definition
table
```

例:

```json
{
  "type": "definition",
  "title": "Write amplification",
  "term": "Write amplification",
  "definition": "論理的な書き込み量より実際の物理書き込み量が増える現象",
  "keyPoints": [
    "LSM compactionで発生する",
    "ストレージ寿命と性能に影響する"
  ],
  "sourceRefs": ["S1", "S2"]
}
```

```json
{
  "type": "table",
  "title": "RedisとMemcached",
  "columns": ["観点", "Redis", "Memcached"],
  "rows": [
    ["永続化", "あり", "基本なし"],
    ["データ型", "複数", "KV中心"]
  ],
  "sourceRefs": ["S1", "S2"]
}
```

package名 `visualization` の大規模renameは今回必須にしない。
概念上は「visual」ではなく **React-renderable structured Map block** として扱う。

## 4. CodexへMap構造化Skillを渡す

### 4.1 Promptだけに全部書かない

現在 `ContextBuilder` に、

```text
図解が理解を改善する場合は lensmap-viz を使える
```

という指示がある。

これを数十行の巨大promptへ育てるのではなく、Map構造化ルールを **Codex Skill** として分離する。

想定配置:

```text
apps/server/skills/
  lensmap-map-composer/
    SKILL.md
    references/
      examples.md
      map-structures.md
```

Skillの責務:

1. 質問と回答内容から `MapSemanticKind` を選ぶ
2. 構造化可能なら必ず構造化する
3. 最小の表現形式を選ぶ
4. 不要な図を増やさない
5. Source IDを対応させる
6. Lensmap JSON DSLを正しく使う
7. Mermaidを使う条件を限定する

### 4.2 Skillに具体例を持たせる

Skillには抽象ルールだけでなくpositive / negative exampleを置く。

例:

```text
質問: Xとは何？
GOOD: definition
BAD: 無意味な1-node flow

質問: AとBの違い
GOOD: comparison + table
BAD: A → B という因果に見える図

質問: A → B → Cの理由
GOOD: causal + flow
BAD: 3列tableだけ

質問: 3製品×3指標
GOOD: quantitative/comparison + table
BAD: 棒グラフを9本並べる

質問: 20時点の推移
GOOD: quantitative + line chart
BAD: 20行tableのみ
```

### 4.3 App Serverへbuilt-in Skill rootを登録する

現在repoに取得済みのCodex App Server protocolには、少なくとも以下がある。

```text
skills/list
skills/extraRoots/set
```

これを利用して、Lensmap Server起動時にbuilt-in Skill directoryを登録する。

想定フロー:

```text
Codex app-server initialize
  ↓
skills/extraRoots/set
  extraRoots = [Lensmap built-in skills directory]
  ↓
skills/list
  ↓
lensmap-map-composer がdiscoverされることをhealth check
  ↓
Reader thread start
```

production buildでもSkill directoryをbundle対象にする。

### 4.4 Lensmap専用Skillを明示的に使わせる

Skillの自動選択だけには依存しない。

Lensmapのbase instructionでは、成功したExplore turnについて `lensmap-map-composer` を利用してMap構造を作ることを明示する。

ただし詳細なdecision tableやexamplesはbase promptへ重複コピーせずSkill側をSSOTにする。

## 5. JSON fenced blockより `lensmap_compose_map` toolを優先する

### 5.1 問題

Codexに最終回答のMarkdown内で、毎回次のようなJSONを書かせる方式でも構造化はできる。

```text
```lensmap-map
{ ... }
```
```

しかしこれは、

- ユーザー向け回答と機械向けpayloadが混ざる
- fenceの閉じ忘れ等に弱い
- JSON schema validationのretryがしづらい
- MapServiceが再びMarkdown parserへ依存する

ため、第一案にはしない。

### 5.2 dynamic toolを使う

既存の `workspace_*` と同じCodex App Server dynamic toolとして、非永続のMap提出toolを追加する。

```text
lensmap_compose_map
```

これはDBへ直接保存するwrite toolではない。
**そのturnのMap DraftをLensmap Serverへ構造データとして提出するだけ**のtoolとする。

そのためReaderのread-only安全モデルを壊さない。

### 5.3 Map Draft schema

概念形:

```ts
interface MapDraft {
  semanticKind: MapSemanticKind;
  title: string;
  conciseExplanation: string;
  primary: StructuredMapBlock;
  supportingBlocks: StructuredMapBlock[];
  sourceRefs: string[];
}
```

`StructuredMapBlock` はallow-listされたdiscriminated unionにする。

初期候補:

```text
definition
table
comparison
flow
hierarchy
timeline
matrix
callout
chart
narrative
```

### 5.4 1 turnの流れ

```text
User question
  ↓
Codex
  ├─ 必要なら workspace_* で追加文脈取得
  ├─ lensmap-map-composer Skillで意味構造を判断
  ├─ lensmap_compose_map(MapDraft) を1回呼ぶ
  └─ ユーザー向け通常回答を返す
        ↓
Assistant message completed
        ↓
MapService
  ├─ 有効なMapDraftがあれば、それをMapArtifactへmaterialize
  └─ MapDraftが無ければ旧Markdown parserへfallback
```

**Map自動保存ポリシーは変更しない。**
成功したAssistant回答は引き続き必ず1つのMapへ自動保存する。

### 5.5 2回目のLLM callは不要

この方式は、

```text
Explore回答
↓
別LLMでMapを再生成
```

ではない。

同じCodex turnの中で、回答を考えたモデル自身がstructured draftをtool callで提出する。

そのため、

- 追加のmodel round tripを原則増やさない
- 回答とMapの意味がずれにくい
- MapServiceでMarkdownを再解釈する必要が減る

という利点がある。

## 6. Source groundingの扱い

`lensmap_compose_map` の `sourceRefs` は必ず `S#` で受ける。

Server側で、既存のper-turn Source registryを使って、

```text
S1 → sourceAnchorId xxx
S2 → sourceAnchorId yyy
```

へ解決する。

存在しない `S99` がdraftにあればvalidation failureとする。

Block単位にも `sourceRefs` を持たせる。

例:

```json
{
  "type": "definition",
  "term": "LSM Tree",
  "definition": "...",
  "sourceRefs": ["S1"]
}
```

これにより、Map全体ではなく**どの構造がどのEvidenceに基づくか**を保持する。

## 7. MapVersion / MapArtifact schemaの変更

対象:

- `packages/shared/src/schemas/map.ts`
- 新規 `map-draft.ts` 等
- repository migration

意味構造はversionごとに変化し得るため、永続化上は `MapVersion` へ次を追加する。

```ts
semanticKind: MapSemanticKind
primaryBlockId: string | null
```

APIの最新 `MapArtifact` view / summaryには、latest versionの `semanticKind` と `primaryBlockId` を投影する。

`primaryBlockId` は「最初に見せる理解」を明示する。Map編集ではblock IDがversionごとに作り直されるため、artifact固定値にはしない。

これによりUIが、現在のような

```text
visual-reference > diagram > chart > table ...
```

という固定heuristicだけで主役を決めなくてよくなる。

例:

- `definition` → definition blockがprimary
- `comparison` → tableがprimary
- `causal` → flowがprimary
- Visual Source画像はEvidenceであり、必ずしもprimaryではない

既存Mapのmigrationでは、blocksからsemanticKindをbest-effort推定し、判断不能なら `synthesis` とする。

## 8. Map生成の具体的な選択ルール

### 8.1 Definition

```text
質問: 「BlueGateとは何？」
semanticKind: definition
primary: definition
```

表示:

```text
BlueGate

remote cache invalidationを……

Key points
• ...
• ...

Evidence
```

図は不要。

### 8.2 Comparison

```text
質問: 「RedisとMemcachedの違い」
semanticKind: comparison
primary: table
```

表示:

| 観点 | Redis | Memcached |
|---|---|---|
| 永続化 | あり | 基本なし |
| データ型 | 複数 | KV中心 |

表だけで十分ならcomparison graphicを追加しない。

### 8.3 Causal

```text
質問: 「なぜcompactionでwrite amplificationが増える？」
semanticKind: causal
primary: flow
```

```text
Compaction
  ↓
既存SSTable再書込
  ↓
物理Write増加
  ↓
Write amplification
```

### 8.4 Process

```text
質問: 「cache miss後のrequest flow」
semanticKind: process
primary: flow
```

```text
Client → CDN → Origin → DB
```

### 8.5 Hierarchy

親子関係が本質の場合のみhierarchy。
小規模ならindent rendererでよい。

### 8.6 Timeline

出来事の時間的前後が意味を持つときだけtimeline。
単なる3-step processはprocess/flowを選ぶ。

### 8.7 Quantitative

数値情報だからchartにする、とはしない。

```text
少数のカテゴリ比較 → table
長い時系列 → line chart
カテゴリ別量比較 → bar chart
2変数の関係 → scatter（意味がある場合のみ）
```

### 8.8 Synthesis

ユーザーの問いが複数の意味構造を横断する場合だけ利用する。

`synthesis` を安易なfallbackにして非構造化文章へ戻さない。
可能な部分は supportingBlocks として定義・table・flow等へ構造化する。

## 9. Maps UIの修正

### 9.1 Maps一覧

latest `MapVersion` からMap summaryへ投影した `semanticKind` と `primaryBlockId` を使って実previewを描画する。

例:

```text
definition → term + definition preview
comparison → mini table
causal/process → mini flow
quantitative → mini chart/table
hierarchy → compact outline
```

現在の `LibraryBig + diagram` placeholderはfallbackのみとする。

### 9.2 Map詳細

変更後:

```text
Title
Primary structured content
Concise explanation
Supporting blocks
Evidence
History / edit metadata
```

Version / Diffを理解内容より上へ置かない。

### 9.3 Editor

raw JSON / Mermaid editorを通常UIから外す。

ユーザー編集は意味レベルに寄せる。

初期版:

- title
- definition / narrative text
- concise explanation

将来:

- 「比較表として整理し直す」
- 「flowとして再構成」
- 「chartではなくtableで表示」

のようなsemantic commandをCodexへ依頼して新versionを作る。

## 15. 実施結果（2026-08-15）

本計画のP0〜P2を実装・検証した。

### P0 — 構造化生成基盤

- `MapSemanticKind` と `MapDraft` / `StructuredMapBlock` schemaを追加した。
- `definition` / `table` を `@lensmap/visualization` の第一級blockとして追加した。
- `lensmap_compose_map` dynamic toolを追加し、1 turnにつき1 Draftだけを受理する。
- tool引数は `mapDraftSchema` からZod JSON Schemaを生成し、runtime validationとtool contractのSSOTを統一した。
- `S#` はper-turn source registryで検証し、存在しないSource IDを拒否する。
- Explore完了時はvalidated DraftをMapServiceへ渡し、Draftが無い場合だけMarkdown parserへfallbackする。
- Map自動保存・`originTurnId`冪等性は維持した。
- `MapVersion` に `semanticKind` / `primaryBlockId` を追加し、既存DB向けmigrationではbest-effort推定を行う。
- `apps/server/skills/lensmap-map-composer/` を追加し、App Server起動時に `skills/extraRoots/set` → `skills/list` でdiscoveryをhealth checkする。
- release bundleへbuilt-in Skill directoryを同梱する。

### P1 — Structured Map UI

- Map詳細を `primary structured content → concise explanation → supporting blocks → history` の順へ変更した。
- raw JSON editorを撤去し、通常編集はtitle / concise explanation / definition・narrative text / tagsに限定した。
- Maps一覧は `primaryBlock` と `semanticKind` を用い、definition / table / flow / hierarchy / timeline / chart / narrativeのsemantic previewを描画する。
- Visual SourceはEvidenceであり、primaryと指定された場合だけ一覧thumbnailの主役になる。
- structured renderer内とMap block外側でEvidenceが二重表示されないようにした。

### P2 — Renderer / Skill品質

- `lensmap-map-composer` にdecision table、positive / negative examples、block selection guideを追加した。
- flow rendererを単純index配置からtopology levelベースの配置へ変更した。
- chart / tableの使い分けをSkillルールと8fixtureで固定した。
- Mermaidは既存fallback / escape hatchとして維持した。
